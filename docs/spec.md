# 受付 Feature Specification

This document is the implementation-ready specification for the new `受付`
workflow. It is based on `agentic_code_docs/reception.txt`, repository
inspection, and the product decisions confirmed during planning.

## 0. Decisions Confirmed During Review

These were resolved against the real codebase and take precedence over any
looser wording elsewhere in this document:

1. **Sidebar** — `受付` is a **second labeled sidebar group** (mirrors the existing
   `メニュー` group). No collapsible/nested `NavItem` support is added.
2. **Assignee pool** — candidates for `担当者` are **all users except those flagged
   `is_hidden_from_workers`** (managers included, self-assignment allowed).
3. **`対応中` visibility** — **all users see all `対応中` cases** (read-only unless
   assigned or a workflow manager).
4. **Card actions** — `やることカード` uses **two separate buttons**, each with its
   own `作業メモ`: `やること完了した` (memo optional) and `引継ぎ` (memo required).
5. **Status storage** — modeled as a PHP enum `App\ReceptionCaseStatus` with a
   Japanese `label()` (mirrors `App\UserRole`). See §5.
6. **"Workflow manager"** — maps exactly to `User::canManageContent()` (Admin +
   Editor). Frontend gates on the already-shared `auth.permissions.manage_content`.

Pending confirmations are listed in §17.

## 1. Goal

Build a lead/reception workflow for work that is not yet a fixed construction
or business schedule.

The current application already handles fixed schedules:

- `ConstructionSchedule`
- `BusinessSchedule`
- `InternalNotice`
- `CleaningDutyRule`

The new workflow must not mix unconfirmed leads into those existing schedule
tables. A lead must be its own domain object until it is manually handled by
staff. V1 does not convert leads into construction or business schedules.

- Database is **SQLite** in dev (file) and test (`:memory:`). `lockForUpdate()` /
  `SELECT ... FOR UPDATE` is a no-op — see §3.2 / §6.3 for the correct approach.

## 3. Main Product Decisions

### 3.1 Lead Object

Create a new domain model for reception leads.

Recommended model name:

- `ReceptionCase`

Do not use the formatted `案件ID` as the database primary key.

Use:

- Database primary key: normal integer `id`
- Public business identifier: `case_number`

Reason:

- The formatted number has business meaning and date-scoped sequencing.
- Primary keys should stay simple, internal, stable, and database-friendly.
- The formatted number can have gaps and should never be reused.

### 3.2 Public 案件ID Format

Pattern:

```text
WJA-C-yyyymmdd-xxxx
```

Example:

```text
WJA-C-20260307-0001
```

Rules:

- `yyyymmdd` is the date when the draft is first created, computed in **JST**
  (`BusinessDate::today()`), not from UTC `now()`.
- `xxxx` is a 4-digit increment scoped to that date.
- Assign this number on first autosave, not on `受付完了`.
- Once assigned, never change it.
- Gaps are acceptable if drafts are deleted or abandoned.
- Do not reuse deleted draft numbers.
- The `WJA-C` prefix is a configurable constant (see §17 Q3).

Implementation guidance (SQLite-safe):

- Add a small daily sequence table, `reception_case_sequences`.
- **Do not use `SELECT ... FOR UPDATE` / `lockForUpdate()`** — it is a no-op on SQLite.
- Generate inside `DB::transaction()`: SQLite serializes writers, so an atomic
  increment of the today row (e.g. `firstOrCreate` then `increment('last_number')`,
  or a single `UPDATE ... SET last_number = last_number + 1`) is safe.
- Add a **unique index on `reception_cases.case_number`** as a correctness backstop;
  on a unique-constraint violation, re-read the sequence and retry once.

### 3.3 V1 Schedule Integration

V1 does not create construction/business schedules from reception cases.

Some reception cases may later need to become construction or business
schedules, but this is out of scope for v1. For now, users handle that manually
outside this feature.

Leave the data model open for future linking, but do not build conversion
actions in v1.

authenticated dashboard redirect to `schedule-overview` should remain.

## 5. Status Model

Use these statuses:

| Status value | UI label | Meaning |
| --- | --- | --- |
| `draft` | `受付下書き` | Autosaved intake draft. |
| `received` | `受付済み` | Reception completed; waiting for workflow manager review. |
| `in_progress` | `対応中` | Assigned user is working on it. |
| `handover` | `引継ぎ` | Assignee requested handover; waiting for workflow manager reassignment. |
| `completed` | `完了` | Work is done and appears only in archive. |

Model this as a PHP enum `App\ReceptionCaseStatus: string` with cases
`Draft`/`Received`/`InProgress`/`Handover`/`Completed`, backing values as in the
table, and a `label()` returning the Japanese UI label (mirrors `App\UserRole`).
Cast it on the model. Add a `canTransitionTo()` helper used by the backend to guard
transitions.

### 5.1 Allowed Transitions

Only these transitions are permitted; the backend must reject anything else
(see §12.3):

| From | To | Trigger | Guard |
| --- | --- | --- | --- |
| `draft` | `received` | `受付完了` (creator) | all required fields present |
| `received` | `in_progress` | `対応開始` (manager) | assignee set |
| `in_progress` | `completed` | `やること完了した` | — |
| `in_progress` | `handover` | `引継ぎ` | `作業メモ` present |
| `handover` | `in_progress` | `対応開始` after reassign (manager) | assignee set |
| `received` / `handover` | `completed` | manager fast-complete (invalid/no-work lead) | manager only |

Explicitly forbidden: `draft → completed`, and any transition out of `completed`
(terminal).

Do not add a separate cancelled/rejected status in v1. If a lead becomes invalid or
needs no further work, a workflow manager completes it (optionally with a `作業メモ`
explaining the outcome).

## 6. Data Model

### 6.1 `reception_cases`

Recommended fields:

- `id`
- `case_number`, unique string
- `status`, indexed string
- `company_name`
- `site_name`
- `reception_document_type_id`
- `reception_content`, text
- `due_on`, date
- `scheduled_on`, nullable date
- `receptor_user_id`
- `assigned_user_id`, nullable
- `completed_at`, nullable datetime
- `completed_by_user_id`, nullable
- `last_activity_at`, datetime
- `created_at`
- `updated_at`

Field label mapping:

| Database field | UI label |
| --- | --- |
| `company_name` | `会社名` |
| `site_name` | `現場名` |
| `reception_document_type_id` | `案件書類` |
| `reception_content` | `受付内容` |
| `due_on` | `期限` |
| `scheduled_on` | `予定日` |
| `assigned_user_id` | `担当者` |

Validation:

- Draft autosave may save partial data.
- `受付完了` requires:
  - `会社名`
  - `現場名`
  - `案件書類`
  - `受付内容`
  - `期限`
- `予定日` is optional.
- `期限` and `予定日` are date-only fields.

### 6.2 `reception_document_types`

This is the master for `案件書類`.

Recommended fields:

- `id`
- `name`, unique
- `sort_order`
- `is_active`
- `created_at`
- `updated_at`

V1 must include an Admin/Editor CRUD page for this master.

Seed common defaults:

- `見積依頼`
- `図面確認`
- `現調依頼`
- `その他`

Inactive document types:

- Should not appear for new cases.
- Should still display correctly on existing cases.

### 6.3 `reception_case_sequences`

Used for public case number generation.

Recommended fields:

- `id`
- `sequence_date`, unique date
- `last_number`
- `created_at`
- `updated_at`

Generation rule:

1. Start a `DB::transaction()` (SQLite serializes writers — no `FOR UPDATE`).
2. `firstOrCreate` the row for today's JST date (`BusinessDate::today()`).
3. Atomically increment `last_number`.
4. Format `WJA-C-yyyymmdd-xxxx`.
5. Create the draft with that `case_number`.
6. Rely on the unique index on `case_number` as a backstop; on collision, retry once.

### 6.4 `reception_case_activities`

Use an activity timeline instead of a single mutable memo field.

Recommended fields:

- `id`
- `reception_case_id`
- `user_id`
- `type`
- `memo`, nullable text
- `from_status`, nullable string
- `to_status`, nullable string
- `from_assigned_user_id`, nullable
- `to_assigned_user_id`, nullable
- `created_at`
- `updated_at`

Recommended activity types:

- `created_draft`
- `submitted`
- `updated`
- `assigned`
- `started`
- `handover_requested`
- `completed`

`作業メモ` rules:

- Store `作業メモ` as activity `memo`.
- The `やること完了した` action's memo is optional.
- The `引継ぎ` action's memo is required (see §8.4 — two separate buttons/forms,
  each with its own `作業メモ`).
- The timeline must show the handover chain and work notes on `やることカード`.

`last_activity_at` bump rule:

- Bump `reception_cases.last_activity_at = now()` when writing these activity types:
  `submitted`, `updated`, `assigned`, `started`, `handover_requested`, `completed`.
- Do **not** bump on draft autosave (drafts are private pre-submission, so seen-state
  is irrelevant).
- On any mutating action, also mark the **acting user** as seen (§6.5) so they do not
  see their own change as new/updated.

### 6.5 `reception_case_seen_states`

Used for last-seen / updated indicators.

Recommended fields:

- `id`
- `reception_case_id`
- `user_id`
- `seen_at`, nullable datetime
- `created_at`
- `updated_at`

Rules:

- Tracking is per user; upsert one row per `(reception_case_id, user_id)`.
- Opening `やることカード` upserts `seen_at = now()` for the current user.
- List pages compare `seen_at` to `reception_cases.last_activity_at`.
- If `seen_at` is null or older than `last_activity_at`, show the case as new
  or updated.
- New-assignee-unseen is **automatic**, not an explicit reset: assignment bumps
  `last_activity_at`, and the new assignee's `seen_at` is null (or older), so the
  case shows as unseen for them without any timestamp reset.

## 7. Permissions

Define a workflow manager as:

```text
Admin or Editor
```

This maps to existing app roles and the existing helper:

- `UserRole::Admin`
- `UserRole::Editor`
- Backend check: `User::canManageContent()`.
- Frontend gate: `auth.permissions.manage_content` (already shared).

The frontend must also receive a per-case `can` map (see §9.4 / §10) so buttons match
exactly what the backend will authorize, rather than re-deriving rules client-side.

### 7.1 Drafts

- Any authenticated verified user can create reception drafts.
- Drafts are visible only to the creator.
- Drafts are editable only by the creator.
- Drafts are deletable only by the creator.
- Workflow managers do not see other users' drafts in v1.

### 7.2 Submitted And Active Cases

After `受付完了`:

- Everyone can read active cases.
- Original receptor can edit case fields.
- Workflow managers can edit case fields.
- Other users are read-only unless assigned.

Assigned users:

- Can view the case.
- Can perform task actions.
- Cannot edit lead fields.

Task actions for assignees:

- Complete the task.
- Request handover.
- Add `作業メモ` through completion or handover action.

Workflow managers:

- Can assign/reassign users.
- Can click `対応開始`.
- Can complete any active task.
- Can recover operational mistakes by editing, reassigning, or completing.
- Can manage document types.

### 7.3 Archive

`アーカイブ画面`:

- Shows all completed cases to all authenticated users.
- Cases are read-only.
- Everyone can open archived detail views read-only.

### 7.4 Assignee Candidates

When a workflow manager assigns/reassigns `担当者`:

- Candidates = all users **except** those flagged `is_hidden_from_workers`.
- Add a `User` query scope for this (mirror the existing `visibleToWorkers` scope),
  e.g. `assignableAsReceptionHandler`.
- Managers may assign themselves; workers (Viewer role) are valid assignees.
- `AssignReceptionCaseRequest` must validate that the chosen id is within this set.

## 8. Page Specifications

### 8.1 受付ホーム

Purpose:

- Lightweight home for reception work.

V1 sections:

- My `受付下書き`
- My active assigned tasks

Do not show an admin-review section on home in v1.

My active assigned tasks:

- Show all assigned non-completed cases.
- Do not limit to due today.
- The section label may be `今日やること`, but behavior is all assigned active
  tasks, matching the confirmed requirement.

Each item should show:

- `案件ID`
- `会社名`
- `現場名`
- `案件書類`
- Status
- `期限`
- `予定日` if present
- New/updated indicator from seen state

### 8.2 受付画面

Purpose:

- Fast intake for new leads.

Behavior:

- Always starts as a new blank form.
- Existing drafts are opened from `受付ホーム` or `やること一覧`.
- First non-empty autosave creates a draft and returns `id` + `case_number`.
- Later autosaves update the same draft.
- Display autosave state clearly:
  - saving
  - saved
  - failed/retry needed
- Do not block typing while autosave is running.

Autosave transport (NEW pattern — the app has no JSON endpoints today):

- `store-draft` and `update-draft` are **plain JSON endpoints** (return a JSON
  response, not `Inertia::render`), authorized via their FormRequest.
  - `store-draft` returns `{ id, case_number }`.
  - `update-draft` returns `{ saved_at }`.
- Client uses Inertia v3 `useHttp`, debounced ~800ms, and keeps its own local state.
- Empty-form guard: do not fire the first `store-draft` until at least one meaningful
  field has content (see §12.2) — opening the page must not create a row.
- On failure, keep local input on screen, show the failed state, retry on next change.

Fields:

- `会社名`
- `現場名`
- `案件書類`
- `受付内容`
- `期限`
- `予定日`

Do not add contact/source fields in v1.

Actions:

- `受付完了`
- Delete/discard draft, only after a draft exists and only by creator

After `受付完了`:

- Status becomes `受付済み`.
- Redirect/reset to a new blank `受付画面`.
- The submitted case appears in `やること一覧`.

### 8.3 やること一覧

Purpose:

- Main active task list.

V1 uses fixed sections only. Do not add search or advanced filters in v1.

Sections:

1. My `受付下書き`
2. Workflow manager review
3. `対応中`

Workflow manager review section:

- Visible only to workflow managers.
- Includes cases with status:
  - `受付済み`
  - `引継ぎ`
- Workflow managers assign/reassign `担当者`.
- Workflow managers may edit case fields.
- Workflow managers explicitly click `対応開始` to set status to `対応中`.
- Merely assigning a user must not automatically start work.

`対応中` section:

- Visible to all users.
- Shows all active `対応中` cases.
- Workflow managers can still edit or override.
- Normal users can open read-only unless assigned.

Each list item should show:

- `案件ID`
- `会社名`
- `現場名`
- `案件書類`
- Status
- `担当者`
- `期限`
- `予定日` if present
- Last activity timestamp
- New/updated indicator

### 8.4 やることカード

Purpose:

- Detail page for one reception task.

On open:

- Mark the case as seen for the current user.

Display:

- `案件ID`
- Status
- `会社名`
- `現場名`
- `案件書類`
- `受付内容`
- `期限`
- `予定日`
- Receptor
- Current assignee
- Activity timeline with `作業メモ`

Actions by status:

- `受付下書き`: creator can edit/delete/submit.
- `受付済み`: receptor and workflow managers can edit; workflow managers can
  assign and start.
- `対応中`: assignee can complete or request handover; workflow managers can
  override.
- `引継ぎ`: workflow managers assign next user and explicitly start again.
- `完了`: read-only.

`対応中` actions UX (two separate buttons, each its own form/`作業メモ`):

- **Completion** — button `やること完了した`, with an optional `作業メモ` textarea.
  On submit → status `完了`, case moves to `アーカイブ画面`.
- **Handover** — button `引継ぎ`, with a **required** `作業メモ` textarea.
  On submit → status `引継ぎ`. A workflow manager later assigns the next user and
  clicks `対応開始`, and the case becomes `対応中` again.
- There is no `引継ぎする` checkbox; the two actions are independent (this resolves
  the wording in `reception.txt`).
- Both memos are stored as `reception_case_activities` (`completed` / `handover_requested`)
  and shown in the timeline, forming the visible handover chain.

Manager overrides on `やることカード` follow §5.1 / §9.4 (assign, `対応開始`, and
fast-complete from `受付済み`/`引継ぎ`).

### 8.5 アーカイブ画面

Purpose:

- Completed task archive.

Rules:

- Only `完了` cases appear here.
- All authenticated users can view all completed cases.
- List and detail are read-only.

Filters:

- Keyword search
- Completion date range

Keyword search should include at minimum:

- `案件ID`
- `会社名`
- `現場名`
- `受付内容`

List ordering:

- Newest completed first.

### 8.6 案件書類マスター

Purpose:

- Manage the pulldown options for `案件書類`.

Access:

- Workflow managers only.

Actions:

- Create
- Rename
- Reorder
- Activate/deactivate

Do not hard delete document types that are used by existing cases.

### 9.4 Policies

Note: the app currently has **no Policy classes** (authorization lives in
FormRequests + inline `abort_unless`). Reception's authorization is record- and
status-dependent (creator vs receptor vs assignee vs manager), so a Policy is the
right tool — this is a deliberate, contained deviation (see §17 Q1 for the
convention-pure alternative).

Add a `ReceptionCasePolicy` whose abilities are the single source of truth, reused
by (a) each FormRequest's `authorize()`, and (b) a per-case `can` map serialized into
Inertia props so the frontend shows exactly the allowed actions.

Policy abilities should cover:

- `viewAny`
- `view`
- `create`
- `update`
- `deleteDraft`
- `submit`
- `assign`
- `start`
- `handover`
- `complete`
- `viewArchive`

Add a `ReceptionDocumentTypePolicy` or equivalent authorization for master CRUD
(gated on `canManageContent()`).

helper (wraps `App\Services\AuditLogger`). Subject = the `ReceptionCase` (or

convention:

- `reception_cases.submitted`
- `reception_cases.updated`

Flash union extensions (`resources/js/types/ui.ts`):

- Extend `FlashResourceAction` with `submitted | assigned | started | handed_over |
  completed` and add the matching Japanese labels wherever
  `recentResourceActionLabel` (or equivalent) maps actions to text.

Layout:

- Keep the workflow utilitarian and task-focused.
- Do not create a marketing/landing page.
- Keep card nesting shallow.
- Text must fit on mobile and desktop.

## 11. List And Sorting Rules

Draft lists:

- Show newest updated first.

Workflow manager review:

- `期限` ascending
- then `updated_at` descending

`対応中`:

- Overdue first
- then `期限` ascending
- then `updated_at` descending

Archive:

- `completed_at` descending

## 12. Edge Cases

### 12.1 Autosave Failure

If autosave fails:

- Keep local input on the screen.
- Show a clear failed state.
- Allow retry on next change or manual retry.
- Do not let the user assume data is saved if the first draft creation failed.

### 12.2 Empty Form

Opening `受付画面` should not create a database record by itself.

Only create the draft after meaningful input exists.

### 12.3 Duplicate Submit

Prevent double `受付完了` submissions.

Backend must enforce the §5.1 transition table via `canTransitionTo()` and reject
invalid transitions, for example:

- Draft to completed directly
- Completed back to active
- Handover without `作業メモ`
- Start without assignee

### 12.4 Deleted Draft

If a draft is deleted:

- The `case_number` is not reused.
- It should not appear in archive.
- It should not appear in active lists.

### 12.5 Assignment Change

When a workflow manager assigns or reassigns:

- Create an `assigned` activity entry (record from/to user ids).
- Update `assigned_user_id`.
- Bump `last_activity_at`.
- The new assignee sees the case as new/unseen automatically (their `seen_at` is
  null or older than the bumped `last_activity_at`) — no explicit seen-state reset.
- Mark the acting manager as seen (§6.5) so their own action isn't flagged new.

## 15. Explicit Out Of Scope For V1

Do not implement these in v1:

- Automatic creation of construction schedules from reception cases.
- Automatic creation of business schedules from reception cases.
- Source/contact fields such as phone, fax, email, caller name.
- Advanced filters on `やること一覧`.
- Admin-review section on `受付ホーム`.
- A separate cancelled/rejected status.
- Using `case_number` as the database primary key.

## 16. Acceptance Criteria

The feature is ready when:

- Any authenticated user can create and submit a reception case without losing
  intake data.
- Drafts are private to their creator.
- Submitted active cases are readable by everyone.
- Workflow managers can review, assign, start, reassign, and complete work.
- Assignees can complete or request handover without editing lead fields.
- Handover uses required `作業メモ`.
- Completed cases appear only in `アーカイブ画面`.
- Last-seen indicators correctly show new/updated cases per user.
- `案件書類` is managed through a master page.
- Tests cover the state transitions, permissions, archive, autosave, and master
  data behavior.
- Existing schedule pages continue to work unchanged.
